## 二、唯一需要澄清的阻断项:`full` 安全阀在首次回填时会误触发

§3.2:

> **`full` 运行时安全阀**:单刊单日新增 >30 条(发文量暴涨,MDPI 系常见)→ 该刊本次自动降级为 `filter` 处理

问题在"单日新增"的判定口径。首次初始化要回填 32 刊各 90 天:

| 刊(full) | 90 天回填量 | 是否 >30 |
|---|---|---|
| JASMS | ≈75 | **是** |
| Phytochemistry | ≈145 | **是** |
| Journal of Natural Products | ≈115 | **是** |
| Horticulture Research | ≈85 | **是** |
| J Mass Spectrometry / RCM / Phytochem Anal | 各 ≈40-60 | **是** |

也就是说,如果实现者把"单日新增"理解为**一次扫描任务的入库量**,首次初始化时**几乎所有 full 刊都会被立刻降级成 filter**——而它们本来正是该用 full 的窄刊。

用户看到的症状是"我明明按建议设了 full,第一次跑完全变成 filter 了",且不会有人想到是安全阀导致的。

**澄清方案**(二选一,写进 §3.2 即可):

- **A(推荐)**:安全阀只对**日常增量窗口**生效——`window_days = (to - from).days ≤ 7` 时才判定;首次回填、新增刊 90 天回填一律跳过安全阀
- **B**:判定口径从"绝对条数"改为"该刊本次新增 ÷ 窗口天数 > 30",即日均阈值

A 更直观,也符合安全阀的本意(防发文量**暴涨**,不是防**历史量大**)。

这一条必须在动工前定下来,否则会污染首次初始化的全部订阅数据,且事后要重新校正模式。

## 三、一处逻辑死锁:无摘要刊被强制 full,又会被安全阀降级

§3.2 的两条规则组合起来会打架:

```
无 abstract → 强制 full        (§3.2 第 124-128 行)
full 单日 >30 → 降级 filter     (§3.2 安全阀)
filter 依赖摘要 → 无摘要刊"形同虚设"
```

三者叠加,一本**高发文量 + 无摘要**的刊就没有合法状态了:full 会灌库,filter 不可用。

当前清单里走 Crossref 的只有 Int J Mass Spectrom(84 条/年),不会触发。但只要用户以后加一本大型 Elsevier 刊(这类刊普遍不给 Crossref 摘要),就会撞上。

**澄清方案**:把"无摘要 → filter 不可用"改成"**无摘要 → filter 降级为仅标题匹配**"。

理由:标题匹配并非形同虚设——`MALDI`、`metabolomics`、`mass spectrometry`、`imaging` 这些词本来就高频出现在标题里,BROAD_TERMS 的标题召回并不低。这样三态自洽:

```
有摘要 + 低发文 → full
有摘要 + 高发文 → filter(标题+摘要)
无摘要(任何发文量)→ filter(仅标题)
```

§3.2 现在把无摘要刊"强制 full"这一步其实可以去掉,直接走仅标题 filter,风险更小。

## 四、一处预期校准:订阅补漏节会比示例大得多

§12 示例写 `订阅补漏(3)`,但按设计推导:

- `filter` 模式入库的论文,**其 `matched_groups` 必然为空**(它是按 BROAD_TERMS 过滤的,不经过检索组)
- 7 本高发文 filter 刊 + 12 本巨刊 = 每天 4-8 条
- 13 本 full 窄刊 = 每天 8-12 条,其中只有少数会被主题检索同时命中

所以「订阅补漏」节实际会是 **12-20 条/天**,可能成为日报里最大的一节,而不是示例里的 3 条。

这不是缺陷(设计意图就是"未命中检索式的确定性补充"),但**示例数字会让人误判规模**。建议把示例改成 `订阅补漏(14)` 量级,或在 §12 加一句"该节通常为日报最大一节,属预期"。

顺带一个可选的优化(不做也不影响开工):full 窄刊的论文其实**不需要**进补漏节——整刊直收意味着"该刊全收",用户对这批的心理预期是"看看有没有漏",与 filter 巨刊的"挑拣"不同。可以考虑给 full 来源单独标 `[整刊]`,不占补漏节。

## 五、其余项:不阻断,可留到实现时处理

## 六、开工建议

按依赖顺序,建议分四步,每步都有可验证的产出:

1. **骨架 + 数据层**:`config.py`(绝对路径)、`store.py`(schema + 迁移)、`queries.py`(IR + Europe PMC 翻译)。验收:单测跑通 IR 翻译与窗口计算
2. **Europe PMC 主题检索跑通**:三组请求 + 分页 + `resultType=core` + errCode 识别。验收:`--dry-run` 打出真实请求串,首次回填 30 天能入库
3. **订阅轨道**:`journals.py`(路由 fallback、BROAD_TERMS、标题黑名单、安全阀)+ `crossref.py`。验收:32 刊初始化入库,模式分布符合预期(13 full / 19 filter)
4. **日报 + GUI**:先 `report.py`(三档 + 补漏节,可无 GUI 验证),再四视图。验收:按 §18 的验收清单逐条过

第 2 步结束时就能生成第一份可读日报,是整条链路上最有价值的早期验证点,建议优先做到那里。
